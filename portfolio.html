Technical Challenges 04

CHALLENGE 01

Supabase JWT를 Spring Security와 직접 통합

문제

Supabase는 자체 Auth 서버가 JWT를 발급하므로, Spring Security의 기본 OAuth2 Resource Server 설정과 구조가 맞지 않았습니다. 특히 HS256 서명 방식과 Supabase 전용 클레임 구조를 표준 필터 체인에 맞게 처리해야 했습니다.

해결

OncePerRequestFilter를 상속한 SupabaseJwtFilter를 직접 구현하여, JJWT 라이브러리로 HS256 검증을 수행하고 SupabasePrincipal(userId, email, role)을 SecurityContext에 주입했습니다. 컨트롤러에서는 @AuthenticationPrincipal로 자연스럽게 접근할 수 있습니다.

결과

프론트엔드 Supabase Auth와 Spring Security가 동일한 JWT를 공유하는 일관된 인증 흐름 확보. 별도 인증 서버 없이 Stateless 구조 유지.

CHALLENGE 02

품목별 공정 일괄 복사 — 트랜잭션 원자성 보장

문제

특정 품목의 전체 공정 라우팅을 다른 품목으로 복사하는 기능에서, 복사 도중 일부만 저장되고 실패하는 부분 커밋 상황이 발생할 수 있었습니다. 또한 대상 품목에 이미 공정이 존재할 경우 기존 데이터와의 충돌 처리가 필요했습니다.

해결

복사 로직 전체를 단일 @Transactional 메서드로 묶고, 복사 전 대상 품목의 기존 공정을 Soft Delete 처리한 뒤 새 공정을 일괄 저장했습니다. Soft Delete 덕분에 실패 시 완전 롤백이 보장됩니다.

결과

복사 작업의 원자성 보장, 실패 시 원본 데이터 보전. 복사 이력 추적 가능.

CHALLENGE 03

서버 상태와 클라이언트 상태의 명확한 분리

문제

초기 설계에서 API 데이터를 Zustand 전역 스토어에 저장하다 보니, 캐시 무효화·로딩 상태·에러 처리를 직접 구현해야 하는 부담과 상태 동기화 버그가 빈번하게 발생했습니다.

해결

서버 상태(API 데이터)는 React Query로 전환하고, Zustand는 인증 세션·UI 상태 (사이드바 열림 여부 등) 클라이언트 상태만 담당하도록 역할을 엄격히 분리했습니다. API 호출은 api/{domain}Api.ts → hooks/use{Domain}Query.ts 2-레이어 구조로 고정했습니다.

결과

자동 캐시 관리·Optimistic Update 활용, 상태 동기화 버그 제거, 컴포넌트 코드량 대폭 감소.

Design Principles & Retrospective 05
주요 설계 원칙

B Backend 일관성

  • 모든 응답 ApiResponse<T> 래핑
  • 비즈니스 예외 BusinessException + ErrorCode enum
  • Soft Delete — deletedAt 필드, entity.delete() 호출
  • Service 기본 @Transactional(readOnly=true)
  • 동적 조건 2개↑ → QueryDSL 사용 원칙
  • MapStruct로 Entity↔DTO 변환 분리

F Frontend 일관성

  • Feature-first 폴더 — 도메인 응집도 최우선
  • 컴포넌트에서 axios 직접 호출 금지
  • 폼은 react-hook-form + zod + @hookform/resolvers
  • TypeScript any 금지 → unknown + 타입 가드
  • enum 대신 as const 패턴
  • 스타일링 Tailwind만, 인라인 style 속성 금지

A API 설계

  • URL 복수형 명사 + 케밥케이스 기준
  • Swagger UI 자동 문서화 (SpringDoc OpenAPI)
  • Vite 프록시로 개발 CORS 없이 백엔드 연결
  • 401 응답 시 axios 인터셉터 자동 로그아웃
  • 공개 엔드포인트 GET /api/health 단 하나

R Realtime

  • Supabase Realtime — PostgreSQL 변경 구독
  • useSupabaseRealtime 커스텀 훅으로 추상화
  • 대시보드 지표 실시간 반영 목표
  • Supabase 대시보드 Replication 활성화 필요
회고

잘 된 점

도메인 기반 패키지 설계로 기능 추가 시 영향 범위를 명확히 격리할 수 있었습니다.

Supabase를 활용해 Auth·DB·Realtime을 별도 인프라 없이 빠르게 통합했습니다.

React Query / Zustand 역할 분리로 상태 관리 코드가 눈에 띄게 단순해졌습니다.

Soft Delete 패턴으로 데이터 이력 추적과 롤백 안전성을 동시에 확보했습니다.

아쉬운 점 / 개선 방향

생산 계획·작업 지시 등 핵심 MES 기능이 아직 미완성 상태입니다.

테스트 커버리지가 핵심 도메인에 집중되어 있어 전체적인 커버리지 확대가 필요합니다.

대시보드 KPI 지표와 Realtime 연동 기능 구현이 남아 있습니다.

운영 배포 시 ddl-auto: validate 전환 및 마이그레이션 전략 수립이 필요합니다.
